# 阿里三 AI 开发全局规则

开发前先读本文件，再读目标仓库的 `AGENTS.md` 和 `docs/ai/project-rules.md`。同一次任务已经读过时不重复读取。

## G-01 先明确再编码

- 写明目标、非目标、假设、验收标准和影响范围。
- 多种解释会导致不同实现时，先请负责人确认。
- 有更简单方案时优先提出，不添加推测性功能。

## G-02 最小且精准的变更

- 每处改动必须能追溯到任务或修复所需。
- 不顺手重构、不改无关格式、不删除无关死代码。
- 只清理由本次改动造成的无用导入、变量或函数。

## G-03 先读项目事实

- 优先读取仓库规则、构建文件、现有实现和测试命令。
- 老项目首次接入或相关结构证据过期时，先建立或局部更新 `docs/ai/project-map.md`，再设计改动。
- 复用项目既有组件、接口约定、错误模型和测试框架。
- 不假设固定接口风格、目录结构、启动命令或数据库类型。

## G-04 凭据和敏感数据

- 凭据仅保存在被版本控制忽略的本地密钥或环境变量文件中，或者公司密钥系统中。
- 禁止把凭据、客户数据写入代码、提示词、日志、报告和截图。
- 发现疑似泄露立即停止传播并报告，不复制原值。

## G-05 高风险操作

- 未经明确授权，不提交、推送、合并、部署或发布。
- 生产或共享数据库永不由智能体自动执行结构或数据变更，只交付脚本和回滚说明。
- 本地开发库变更也必须可回滚，并在执行前说明影响。
- 不执行破坏性 Git 或文件命令来清理现场。

## G-06 智能体隔离

- 只读分析可以在当前工作树并行。
- 修改代码的智能体默认使用独立子工作树。
- 同一文件同一时刻只有一个写入智能体；共享文件必须指定唯一负责人。
- 每个智能体只获得完成任务所需的最小范围和上下文。

## G-07 测试独立性

- 单元测试是白盒测试，可读取实现，覆盖变动逻辑的正常、边界和异常路径。
- 验收/E2E 用例从需求和验收标准生成，不用实现代码反推期望结果。
- 只验证受影响范围和必要冒烟路径，除非风险要求全量回归。

## G-08 缺陷修复

- 修改前先稳定复现，记录现象、证据和根因假设。
- 将根因归为实现缺陷、测试缺陷、环境问题或需求偏差。
- 只实施与已确认根因一致的最小修复，并添加回归验证。
- 同一问题连续三轮没有进展时停止试错，提交现场和决策点。

## G-09 审查门禁

- 审查只覆盖当前任务差异及其直接影响。
- 发现按阻断、严重、一般分级，并提供文件、行号和触发条件。
- 阻断与严重问题必须修复并复审；一般问题可记录后续处理。

## G-10 证据化交付

- 交付说明必须列出改动、实际验证、未验证项和剩余风险。
- 不把“命令执行成功”写成“功能一定正确”。
- 不伪造测试、覆盖率、审查或人工确认结果。
- 功能、缺陷和行为变更必须在 `docs/ai/runs/<任务编号>/` 维护需求计划、实施计划、编码计划、测试用例、单测报告、自动化测试报告、审查报告和交付报告。
- 建立 `AC → DEV → 代码 → TC → 执行结果` 追踪；测试报告必须逐用例记录状态和证据，不能只给通过率或总数。
- 文档从对应阶段开始维护，不允许在任务结束后根据实现反向编造需求、用例或执行记录。

## G-11 人工门禁

需求和验收确认、重大架构取舍、生产操作、提交推送、合并和发布由人最终决定。智能体可准备证据与建议，不能替代责任人签字。
