# 阿里三多智能体开发

执行与具体项目无关的开发流程。不得假设目标项目使用 RuoYi、Java、某种前端框架、固定目录或固定命令。

## 执行前硬门禁

以下约束优先于后文所有“自动”“并行”和效率建议：

1. 当前工作树必须同时存在根目录 `AGENTS.md`、`docs/ai/project-rules.md` 和 `.agents/skills/ali3-dev/SKILL.md`。任一缺失时立即停止，只报告“项目规则未随当前工作树安装或提交”，不得用全局 Skill 代替项目规则继续扫描、规划或编码。
2. **Agent** 包括 Orca 工作 Agent、子工作树 Agent、模型内置子 Agent、`Task`/`Explore` Agent、后台 Agent、只读 Agent及任何其他委派执行者。首次创建其中任何一种之前，必须展示用途和数量并等待用户选择；“只读”“后台运行”或用户创建了主控工作树都不构成授权。
3. 老项目缺少可信项目地图时，先创建 `docs/ai/runs/<任务编号>/00-run-plan.md`，记录当前状态、识别范围和待选择的 Agent 启动方式。需要并行识别时只询问并等待：

   ```text
   老项目结构识别需要工作 Agent，请选择：
   1. 主控创建并调度只读甲乙
   2. 我手动创建
   3. 不创建 Agent，由主控独立识别
   ```

4. 未完成 `docs/ai/project-map.md`、`01-requirement-plan.md`、`02-implementation-plan.md`、`03-coding-plan.md`、`04-test-cases.md` 并获得 G1 明确确认前，不得修改业务代码、启动写入 Agent、创建写入工作树或声称进入开发阶段。
5. 主控是上述治理文档的唯一写入者。分析 Agent 只返回证据；结果返回后必须先落盘，再向用户报告，不能把“稍后生成文档”作为通过门禁。

## 一句话功能入口

用户只需要描述需求：

```text
使用 $ali3-dev 开发功能：<需求描述>
```

收到“开发、新增、实现某功能”一类请求时，自动进入五环节流程，不要求用户重复项目路径、选择工作模式、指定智能体分工或粘贴编排提示词：

1. 将当前仓库作为目标项目，先执行“执行前硬门禁”，再读取现有项目规则并检查未提交改动；保留并隔离用户已有改动。
2. 自动判断新项目或老项目。老项目地图缺失、过期或未覆盖当前模块时，读取 [老项目结构识别](references/legacy-project-discovery.md)。
3. 需要 Orca 时读取 [Orca 五环节编排](references/orca-orchestration.md) 和当前版本的 `orca skills get orchestration` 说明。
4. 读取 [可审计交付物与追踪规则](references/delivery-evidence.md)，创建 `docs/ai/runs/<任务编号>/`，先生成执行计划、需求计划、实施计划、编码计划和测试用例。
5. 老项目识别默认由主控独立完成；如确需并行调查，必须按硬门禁先让用户在“主控创建”“手动创建”“主控独立完成”之间选择，未回复前不得调用任何内置或外部子 Agent。
6. 主控汇总项目地图、验收标准、共享契约、任务依赖、文件所有权、验证命令和风险，并建立 AC→DEV→TC 的追踪关系。
7. 展示简明摘要和上述文档路径，在 G1 用一个短问题确认计划和 Agent 启动方式；选择结果写入实施计划。确认前不得修改业务代码或创建工作 Agent。
8. 用户选择“主控创建并调度”时，主控按已确认的 Agent/模型或 Orca 当前默认配置创建并监督甲乙；选择“用户手动创建”时，主控只输出任务单并等待用户创建。随后执行环节 2 至环节 4。
9. 完成后生成交付报告并停在环节 5；不自行提交、推送、合并、部署或操作生产/共享数据库。

如果需求信息足以形成可验证计划，不追加形式化问题；信息不足时只询问会改变实现或验收结果的关键问题。

## 每次任务开始

1. 读取目标仓库的 `AGENTS.md`、`docs/ai/project-rules.md` 以及相关构建和测试配置。每项内容在同一任务中只读取一次，除非文件发生变化。
2. 判断是新项目还是老项目。老项目的项目地图缺失、过期或未覆盖当前模块时，先读取 [老项目结构识别](references/legacy-project-discovery.md)，完成识别后再制定任务计划。
3. 明确目标、非目标、假设、验收标准、影响范围和成功判据。只有歧义会实质改变实现时，才在编码前询问。
4. 选择一个主要模式：**规划**、**实现**、**审查**或**修复**，只读取对应的参考文件。
5. 对功能、缺陷和行为变更读取 [可审计交付物与追踪规则](references/delivery-evidence.md)，从任务开始维护磁盘产物，不在结束时倒推补写。
6. 始终遵守：最小改动、一个文件只有一个写入智能体、写入智能体使用隔离工作树、权限设为人工确认、所有结论提供证据；未经明确授权不得提交、推送、合并或部署。

## 专项工作模式

只有用户明确要求单独规划、审查、修复或实施既有计划时，才直接进入对应专项模式；普通新增功能优先使用上面的一句话入口。

用户可以继续通过本 Skill 指定模式，也可以使用同仓库的快捷独立 Skill：

```text
$ali3-plan <需求描述>
$ali3-implement [DEV编号]
$ali3-review
$ali3-fix <问题现象或失败TC>
```

快捷 Skill 自动定位当前仓库和唯一活动任务，不要求用户重复任务目录或内部流程；只有多个候选会导致不同操作时才询问一个简短选择问题。

- **规划**：读取 [规划模式](references/planning.md)，输出任务简报、依赖图、文件所有权、门禁和验证命令，不修改业务代码。
- **实现**：读取 [实现模式](references/implementation.md)，验收标准确认后，使用最少且安全的工作树完成实现。
- **审查**：读取 [审查模式](references/review.md)，除非用户另行授权修复，否则保持只读。
- **修复**：读取 [修复模式](references/bug-fix.md)，修改代码前必须稳定复现并确认根因。

需要使用 Orca 工作智能体时，还要读取 [Orca 五环节编排](references/orca-orchestration.md)。修改 Orca 编排状态前，先运行 `orca skills get orchestration`，并以当前输出为准；只有当前说明要求时才读取对应扩展参考。

## 开发门禁

不得静默跳过以下门禁：

1. **G0 准备完成**：已读取仓库规则并确认真实命令；老项目相关结构、复用资产和运行状态已经识别；任务不包含明文凭据；`00-run-plan.md` 已创建。
2. **G1 计划确认**：`01-requirement-plan.md`、`02-implementation-plan.md`、`03-coding-plan.md`、`04-test-cases.md` 已完成；AC→DEV→TC 可追踪；文件所有权、依赖、高风险操作和 Agent 启动方式已经人工确认。
3. **G2 实现验证**：编码计划已按实际状态更新；每个写入智能体的差异都没有越界；`05-unit-test-report.md` 有真实命令、结果和证据。
4. **G3 审查通过**：`06-automation-test-report.md` 和 `07-review-report.md` 已完成；独立审查不存在未关闭的阻断或严重问题。
5. **G4 人工集成**：`08-delivery-report.md` 已建立 AC→DEV→代码→TC→结果追踪；由开发者决定是否提交、合并、推送、部署以及执行生产或数据库操作。

需要多智能体时，主控建议最少有效数量并生成自包含任务单，然后询问 Agent 启动方式。用户可选择由主控创建和监督，或自行创建和控制；未选择前不得启动。工作智能体可在实现、测试和交叉审查阶段复用角色。

## 安全边界

- 不得在提示词、日志、代码、报告或截图中暴露凭据和客户数据。
- 不得对生产或共享数据库自动执行数据定义或数据修改语句，只能提供经过审查的脚本和回滚说明。
- 工作树只提供代码隔离，不是安全沙箱。
- 保留用户已有的无关改动，不得擅自清理、重置或改写。
- 同一根因假设连续三次尝试仍无进展时停止，提交证据以及需要人工决定的问题。

## 交付要求

只报告有证据支持的结果，并按 [可审计交付物与追踪规则](references/delivery-evidence.md) 落盘：

- 修改了哪些文件及原因；
- 实际执行了哪些检查及结果；
- 审查发现及关闭状态；
- 未验证内容、剩余风险和人工下一步。

功能、缺陷和行为变更必须使用 `assets/` 中的执行计划、需求计划、实施计划、编码计划、测试用例、单测报告、自动化测试报告、审查报告和交付报告模板。不得编造测试结果，不得只报告通过数量而缺少逐用例证据，也不得代替人工把人工门禁标记为已确认。
