# 修复模式

## 修改前诊断

1. 记录环境、失败行为、期望行为和最小稳定复现步骤。
2. 收集聚焦证据，例如失败断言、接口响应、日志、截图、调用链或相关代码位置，并对凭据和客户数据脱敏。
3. 建立可验证的假设，将根因归类为实现缺陷、测试缺陷、环境问题或需求偏差。
4. 修改前先写出根因结论。如果证据无法区分会导致不同修复的假设，提交人工决定。

使用 `assets/root-cause-report.md` 在本次任务目录生成 `root-cause-report.md`，关联失败 TC、AC、DEV 和证据路径。

## 实施修复

- 只修改能够解决已证实根因的内容。
- 条件允许时，增加一个能够复现原问题并在修复后通过的回归测试。
- 重跑失败用例、受影响测试和小范围冒烟测试。
- 不得通过削弱断言或隐藏错误来让测试变绿。
- 更新 `03-coding-plan.md` 的修复状态，并把修复前失败、修复版本、复测命令与结果写入 `06-automation-test-report.md`。

## 尝试次数限制

每轮记录假设、改动和结果。同一问题连续三轮没有进展时停止，提交复现步骤、证据、已尝试修复、剩余假设和需要人工决定的问题。

所有失败闭环都要保存根因和复测证据；无失败时不创建空的根因报告。
