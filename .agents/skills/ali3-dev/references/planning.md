# 规划模式

## 输入材料

读取需求、仓库规则、相关代码和配置以及现有测试。老项目先读取 `docs/ai/project-map.md`；地图缺失、过期或未覆盖本次模块时，先执行 `legacy-project-discovery.md`。存在独立验收来源时，不得从实现代码反推需求。

## 并行只读分析

并行分析不是默认授权。首次使用任何 Orca、内置、后台或只读子 Agent 前，先创建 `00-run-plan.md` 并等待用户选择 Agent 启动方式；未选择时由主控独立分析或停下等待，不得自动委派。

只有分析范围相互独立时才创建不同的分析智能体，例如：

- 架构和依赖影响；
- 测试和回归影响；
- 安全、权限、数据和迁移风险；
- 现有组件和项目约定的复用情况。

所有分析智能体保持只读，可以共用当前工作树。要求每个智能体给出证据路径、不确定项和建议边界；不要让多个智能体回答同一个宽泛问题。

## 产出计划

读取 `delivery-evidence.md`，先创建 `docs/ai/runs/<任务编号>/00-run-plan.md`，再使用资源模板形成四份 G1 必需产物：

1. `01-requirement-plan.md`：原始需求、目标/非目标、UC、可断言 AC、假设、疑点和需求变更记录；
2. `02-implementation-plan.md`：现状证据、复用资产、方案取舍、接口/数据/权限契约、任务依赖、风险与回滚；
3. `03-coding-plan.md`：DEV 编号、关联 AC、文件级修改范围、唯一负责人、顺序、验证命令和状态；
4. `04-test-cases.md`：依据需求和 AC 独立生成测试用例，建立 AC×TC 双向覆盖矩阵，不从实现代码反推期望。

必要时使用 `task-brief.md` 为工作智能体生成自包含任务单。上述计划必须覆盖：

1. 目标、非目标、来源、假设和待决定事项；
2. 带稳定编号的可观察验收标准及验证方式；
3. 最小且可独立验证的子任务和依赖；
4. 精确到目录或文件的写入所有权，以及集成顺序；
5. 项目实际使用的单元测试、静态检查、集成测试和冒烟测试命令；
6. 破坏性操作、数据库、安全和兼容性风险；
7. 需要人工确认的门禁。

每条 AC 至少关联一个 DEV 和一个 TC；尚不能自动化的 TC 仍须保留，写明人工步骤、阻塞原因和风险。

只有写入范围不重叠的任务才可以并行。共享入口、数据库结构、依赖锁文件、生成的客户端和中心配置必须交给唯一的集成负责人。

## 结束条件

结束前先把项目地图和所有 G1 产物真实写入磁盘，再展示摘要。不得先在聊天中宣布计划、启动开发或承诺“稍后补文档”。

展示计划摘要、四份文档路径、建议的 Agent 数量、角色、模型选择原则和任务单，然后只询问：

```text
Agent 启动方式请选择：
1. 主控创建并调度
2. 我手动创建
```

用户可在选项 1 后补充甲乙执行器、模型和推理强度；未补充时使用 Orca 当前默认配置，并在实施计划记录实际选择。未获得选择前不得创建 Agent。规划专项模式只记录选择并停在 G1；完整开发流程在 G1 确认后按选择执行。
