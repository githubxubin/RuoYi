# 审查模式

保持只读。依据已确认的验收标准、仓库规则、直接调用方和相关测试审查当前任务差异。除非无关存量代码会导致本次变更不安全，否则不要扩大审查范围。

开始前读取本任务的需求计划、实施计划、编码计划、测试用例、单测报告和自动化测试报告，核对文档与实际差异是否一致；文档声称已完成但缺少命令或证据，按严重问题处理。

## 检查内容

1. **正确性**：行为、边界条件、并发、幂等性和兼容性。
2. **安全性**：鉴权、注入、不安全反序列化、凭据或客户数据泄露、敏感日志。
3. **失败处理**：输入校验、异常吞没、资源释放、重试和部分成功状态。
4. **项目一致性**：复用现有组件和契约，遵守项目约定，不增加推测性抽象。
5. **测试充分性**：覆盖变更行为和重要失败路径；断言证明外部行为，而不是照抄实现。
6. **运行与数据安全**：迁移、回滚、可观测性，以及生产和共享系统边界。
7. **追踪完整性**：每条 AC 能映射到 DEV、实际代码、TC 和执行结果；不存在静默未测或伪造通过。

## 问题分级

只报告可执行的问题，并给出精确文件和行号、触发输入或操作序列、影响以及具体修复建议。

- **阻断**：可利用的安全漏洞、凭据泄露、数据丢失或核心功能不可用。
- **严重**：真实的正确性或回归问题、缺少必要鉴权或校验，或者必需行为没有得到验证。
- **一般**：有明确收益但不阻塞交付的可维护性或项目约定问题。

使用 `assets/review-report.md` 写入 `07-review-report.md`。不得把个人风格偏好包装成问题。没有发现时，应明确说明，并列出剩余风险或未执行检查。只有不存在未关闭的阻断和严重问题，且自动化测试报告逐 TC 有证据时，G3 才通过。
