# 实现模式

## 前置条件

- G1 已确认，或者需求没有实质歧义并且用户明确要求实施。
- 已读取仓库规则并确认真实命令。
- 文件所有权不存在写入重叠。
- `01-requirement-plan.md` 至 `04-test-cases.md` 已完成且 AC→DEV→TC 可追踪。
- 已读取 `efficiency.md`，大型任务已确认本次实施阶段。

## 分配任务

- 使用能够产生有效并行的最少 Orca 写入智能体；禁止调用模型或 CLI 内置子 Agent及其私有工作树。
- 为每个写入智能体明确一个结果、允许路径、禁止路径、前置依赖、验收标准和必跑检查。
- 每个写入智能体使用独立子工作树；只读辅助智能体可以共用当前工作树。
- 共享文件由唯一集成负责人修改；有依赖的工作必须串行，不得猜测上游接口。
- 读取实施计划中的 Agent 启动方式。选择“主控创建并调度”时，主控按已确认配置或 Orca 当前默认配置启动并监督；选择“用户手动创建”时，主控只提供任务单并等待。缺少选择时不得启动工作 Agent。

## 写入智能体循环

1. 只检查与任务相关的现有实现和测试。
2. 完成最小改动，保持项目风格并保留用户的无关修改。
3. 为变更行为新增或更新测试，覆盖有意义的正常、边界和失败路径。
4. 只运行能够证明子任务的最小定向检查；外部数据库、浏览器 E2E、真实 API 和全量回归留给主控验收。
5. 返回修改文件、原因、命令结果、风险和未完成项。未经授权不得提交。

主控将返回内容写入 `03-coding-plan.md` 的状态和实际变更列，并把真实单元测试命令、退出码、结果、覆盖信息和证据路径写入 `05-unit-test-report.md`。工作智能体不得各自修改治理文档。

## 集成

主控智能体在合并工作前检查每个差异是否越界。按依赖顺序集成，共享文件由集成负责人统一处理，然后在集成工作树运行一次受影响模块测试和一次必要的全工程编译。相关代码未变化时复用已有通过证据，不重复执行。

把集成后的差异交给独立审查智能体。发现未关闭的阻断或严重问题时，退回对应写入智能体修复，随后重跑受影响检查并进行定向复审。

集成验证按 `04-test-cases.md` 分层执行。先定向自动化，再按风险进入数据库、E2E、真实外部 API 和回归；环境缺失的用例直接标为阻塞或未执行，不在开发阶段等待或搭建。失败时先定向复测，最多两轮后停止并提交证据。

## 结束条件

只有 G2 和 G3 都通过，才能认为实现完成。主控随后更新 `08-delivery-report.md` 的 AC→DEV→代码→TC→结果矩阵。提交、合并、推送、部署和生产或数据库操作仍属于 G4 人工动作。
