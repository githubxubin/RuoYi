# Orca 五环节多智能体编排

本编排固定为五个环节。主控负责计划、文档和门禁；开发人员在 G1 选择由主控创建并调度工作 Agent，或由自己手动创建。流程阶段用于控制质量，不为每个阶段创建新智能体；已创建的工作智能体可在不同阶段复用角色。Orca 是唯一外层编排器。

```text
1. 需求与任务计划
          ↓
2. 甲乙并行开发
          ↓
3. 集成与交叉审查
          ↓
4. 验收与修复
          ↓
5. 人工合并
```

## 默认拓扑

```text
开发人员（选择 Agent 控制方式、确认门禁和最终合并）
├── 主控智能体（分析、计划、任务单、治理文档、集成判断）
├── 工作智能体甲（由开发人员按任务创建）
└── 工作智能体乙（按需创建，不强制）
```

核心原则：

> 独立任务立即并行；存在前置依赖、共享契约未确定或文件所有权冲突时才串行。

工作树结构：

```text
master（受保护，只接受人工最终合并）
└── task-<编号>-integration（主控与集成候选）
    ├── task-<编号>-a（工作智能体甲）
    └── task-<编号>-b（工作智能体乙）
```

## 环节 1：需求与任务计划

### 主控负责

1. 读取项目规则、需求来源和真实构建/测试配置。
2. 判断新项目还是老项目。
3. 形成目标、非目标、假设和可测试验收标准。
4. 确认接口、数据和权限等共享契约。
5. 将工作拆成最少且可独立验证的 DEV 任务，分配互不重叠的文件所有权。
6. 从需求和 AC 独立生成 TC，给出验证命令、风险和人工确认点。
7. 建立 `docs/ai/runs/<任务编号>/` 和 AC→DEV→TC 追踪。

### 老项目条件活动

老项目没有可信项目地图、项目地图未覆盖本次模块或结构证据过期时，先执行 [老项目结构识别](legacy-project-discovery.md)：

```text
主控：确定范围、汇总项目地图
├── 甲：代码结构、模块边界、前后端结构、公共资产
└── 乙：运行、接口、数据、鉴权、测试和环境验证
```

需要并行调查时，主控在任何委派之前先创建 `00-run-plan.md` 并询问 Agent 启动方式；此处 Agent 同时包括 Orca Agent和模型内置/后台/只读子 Agent。用户选择主控模式后可由主控创建只读甲乙，选择手动模式则只输出任务单，选择主控独立识别则不创建任何 Agent。未获得选择不得委派。识别结果返回后，主控必须立即生成 `docs/ai/project-map.md`，不能等到开发开始后补写。

已有可信项目地图时只抽样核对本次模块，不重复全量扫描。

### 其他条件活动

- 涉及 UI：读取设计稿/Figma，只盘点本次页面和共享组件。
- 涉及数据库：确认迁移、回滚、数据兼容和人工授权边界。
- 重大架构或安全决策：增加独立模型评审，不作为普通任务默认步骤。

### 第 1 环节产物和门禁

按 `delivery-evidence.md` 产出：

- `00-run-plan.md`；
- `01-requirement-plan.md`；
- `02-implementation-plan.md`；
- `03-coding-plan.md`；
- `04-test-cases.md`；
- 必要的甲乙自包含任务单。

文档缺失、AC 无法断言、AC 未映射 DEV/TC、文件所有权重叠或 Agent 启动方式未选择时不得通过 G1。聊天中的分析摘要不算文档产物。人工确认任务计划和启动方式后才能进入环节 2；此前不得修改业务代码或创建写入工作树。

## 环节 2：甲乙并行开发

按实施计划执行：

- **主控创建并调度**：主控读取当前 `orca skills get orchestration`，按用户确认的配置启动所需 Agent；未指定模型时使用 Orca 默认并记录实际值。主控负责消息、结果收集和异常升级。
- **用户手动创建**：主控输出任务单和工作树建议，等待用户创建后再继续；不得代为启动。

两种方式都要求各 Agent 在独立子工作树完成自己的代码、单元测试和定向检查。

### 前后端或多模块功能

```text
甲：后端/模块 A + 对应单元测试
乙：前端/模块 B + 对应单元测试
```

### 单模块功能

```text
甲：实现功能 + 单元测试
乙：根据需求并行设计验收、边界和异常用例（只读）
```

### 缺陷修复

```text
甲：建立稳定复现和回归用例
乙：分析日志、调用链和可证伪根因假设
```

### 并行约束

满足以下条件才并行写入：

- 输出可以独立验证；
- 修改文件不重叠；
- 共享接口和数据契约已经确定；
- 一方不需要等待另一方的实现结果。

数据库迁移、依赖锁文件、中心配置、公共入口和共享契约只能指定一个负责人。无法划分独占文件时，一个智能体写代码，另一个转为测试设计或只读分析。

甲乙必须返回：关联 DEV/AC、修改文件、修改原因、实际命令和结果、证据路径、未验证项、剩余风险。主控据此更新 `03-coding-plan.md` 和 `05-unit-test-report.md`。

## 环节 3：集成与交叉审查

主控把甲乙结果组合到任务集成工作树，处理共享文件和冲突，运行最小集成检查。

随后交叉审查：

```text
甲审查乙负责的代码范围
乙审查甲负责的代码范围
主控检查整体契约、集成结果和范围越界
```

审查内容：

- 是否符合验收标准和共享契约；
- 正确性、边界、异常和并发；
- 鉴权、权限、输入校验和敏感信息；
- 是否复用老项目现有组件、错误模型和基础设施；
- 测试是否覆盖变更行为；
- 是否出现任务范围外修改。

问题分为阻断、严重、一般。阻断和严重问题退回原文件负责人修复，重跑受影响测试后定向复审；清零后进入环节 4。

主控将审查范围、发现、修复和复审状态写入 `07-review-report.md`，不得以聊天摘要代替归档报告。

## 环节 4：验收与修复

根据风险选择验证范围，不默认执行所有测试：

- 始终执行：受影响单元测试、静态检查、核心冒烟测试；
- 用户可见流程：执行对应 E2E/验收测试；
- 公共模块、契约或高风险改动：扩大受影响回归；
- 发布前或重大变更：执行全量回归。

验收用例依据需求和验收标准生成，不从实现代码反推期望。测试失败时：

```text
稳定复现 → 收集证据 → 根因分类 → 最小修复 → 失败用例 + 冒烟复测
```

根因分类为实现缺陷、测试缺陷、环境问题或需求偏差。同一根因假设连续三轮无进展时停止，提交证据和人工决策点。

环节结束时输出：测试结果、未验证项、剩余风险、必要回滚说明和审查结论。

测试必须以 `04-test-cases.md` 为执行清单，逐 TC 把状态、实际结果和日志/截图/机器报告路径写入 `06-automation-test-report.md`。只有汇总数字、没有逐用例证据时不得通过门禁。发生失败时生成根因报告并把修复版本与复测结果回写测试报告。

## 环节 5：人工合并

由开发人员检查集成候选和证据，决定：

- 是否提交或保留本地提交；
- 是否合并到 `master`；
- 是否推送远程仓库；
- 是否进入部署或发布流程；
- 是否执行数据库脚本。

主控在此之前生成 `08-delivery-report.md`，至少包含 AC→DEV→实际代码→TC→最近结果追踪矩阵、未验证项、剩余风险和回滚说明。

智能体不得代替人工完成最终合并、推送、部署、发布或生产/共享数据库操作。

只有本次出现真实、可复用的新经验时才记录经验；不为每个普通任务机械生成经验报告。

## 强制产物

```text
docs/ai/
├── project-map.md                  # 老项目按需生成和局部更新
└── runs/<任务编号>/
    ├── 00-run-plan.md
    ├── 01-requirement-plan.md
    ├── 02-implementation-plan.md
    ├── 03-coding-plan.md
    ├── 04-test-cases.md
    ├── 05-unit-test-report.md
    ├── 06-automation-test-report.md
    ├── 07-review-report.md
    ├── 08-delivery-report.md
    ├── root-cause-report.md        # 仅发生失败时
    └── evidence/
```

极小且无行为变化的任务可以按 `delivery-evidence.md` 合并规划文档，但必须保留追踪、测试和审查证据以及裁剪理由。

## 自包含任务单

主控给甲乙的任务单必须包含：

```text
任务目标：
非目标：
前置依赖和已确认契约：
允许修改范围：
禁止修改范围：
验收标准：
必跑验证命令：
提交权限：默认不允许；若允许，仅限当前子分支本地提交
交付内容：修改文件、原因、命令与结果、未验证项、风险
```

缺少文件所有权或完成判据时，不启动写入任务。

## Orca 执行规则

编排前只读取一次当前版本说明：

```bash
orca skills get orchestration
```

G1 必须先提出并记录选择：

```text
Agent 启动方式请选择：
1. 主控创建并调度
2. 我手动创建
```

选择主控模式后才按当前 `orca skills get orchestration` 执行；用户可以同时指定甲乙执行器、模型和推理强度，未指定则使用 Orca 默认配置。选择手动模式时只展示工作树名、配置建议和任务单。主控模式启动后结束当前轮次，由 Orca 在结果、提问或升级时唤醒主控，禁止高频轮询。

## 禁止事项

- 不增加第六个固定主流程环节。
- 不为老项目识别、测试或审查单独创建长期固定智能体。
- 不让甲乙同时修改同一文件。
- 不在工作智能体内部启动第二套总编排。
- 不让测试结果反向修改已确认的验收标准。
- 不让智能体自行推送、合并、部署或操作生产和共享数据。
- 未选择 Agent 启动方式前，不让主控创建 Agent 或工作树；主控模式下未指定模型时只使用并记录 Orca 默认值，不自行臆测模型名。
- 不以聊天中的“测试通过”代替测试用例、逐用例结果和证据文件。
