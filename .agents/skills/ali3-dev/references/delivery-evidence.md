# 可审计交付物与追踪规则

功能开发、缺陷修复和有行为变化的代码修改必须留下可复核的磁盘产物。文档是门禁输入和执行状态源，不得在结束时根据代码倒推补写。纯只读咨询或不改变行为的微小文案修改可以精简正文，但必须在执行计划中写明裁剪理由。

## 目录与责任

每次任务使用稳定任务编号，产物统一保存到：

```text
docs/ai/runs/<任务编号>/
├── 00-run-plan.md
├── 01-requirement-plan.md
├── 02-implementation-plan.md
├── 03-coding-plan.md
├── 04-test-cases.md
├── 05-unit-test-report.md
├── 06-automation-test-report.md
├── 07-review-report.md
├── 08-delivery-report.md
├── root-cause-report.md          # 仅出现失败并进入修复时
└── evidence/                     # 日志、截图、覆盖率、机器报告等
```

主控智能体是这些治理文档的唯一写入者。工作智能体只返回结构化结果和证据路径，由主控汇总，避免多个工作树同时改同一报告。业务代码与测试代码仍按文件所有权分配。

## 简洁与单一事实源

治理文档用于决策和追踪，不用于复述全部分析。默认遵守：项目地图不超过 250 行；`00`～`04` 每份不超过 120 行；任务单不超过 100 行。超出时在 `00-run-plan.md` 写明风险驱动的必要原因。

- 需求只在 `01` 完整描述；其他文档引用 AC。
- 方案和契约只在 `02` 完整描述；`03` 只记录任务、所有权、状态和验证。
- 测试步骤只在 `04` 完整描述；`05`～`08` 只记录结果和引用。
- 日志、XML、截图和长命令输出只放 `evidence/`，报告不粘贴全文。
- 不为填满模板重复背景、代码签名、表结构或同一风险。

## 各产物的生成时机

| 产物 | 最晚生成时间 | 核心内容 | 放行条件 |
|---|---|---|---|
| `00-run-plan.md` | 任务开始 | 五环节状态、负责人、门禁、产物链接、变更记录 | 当前步骤和阻塞原因可定位 |
| `01-requirement-plan.md` | G1 前 | 原始需求、范围、UC/AC、假设、疑点、影响范围 | 每条 AC 可观察、可断言 |
| `02-implementation-plan.md` | G1 前 | 方案、复用资产、接口/数据/权限契约、依赖、任务拆分、回滚 | 关键契约已确认，风险有处置 |
| `03-coding-plan.md` | G1 前建立，编码中更新 | 文件级任务、唯一负责人、顺序、状态、验证命令 | 文件所有权无重叠，任务可独立验证 |
| `04-test-cases.md` | G1 前 | 从需求和 AC 生成的单元/接口/E2E/手工用例及测试数据 | 每条 AC 至少映射一条 TC，未覆盖项有理由 |
| `05-unit-test-report.md` | G2 前 | 命令、环境、通过/失败、覆盖率、未覆盖项、证据 | 受影响单测通过，或失败已明确阻断 |
| `06-automation-test-report.md` | G3/G4 前 | 按 TC 的自动化结果、命令、时间、证据、失败分类和复测 | 不得只写总数；每条执行用例可追溯 |
| `07-review-report.md` | G3 前 | 差异范围、分级问题、修复与复审状态 | 阻断和严重问题清零 |
| `08-delivery-report.md` | G4 前 | AC→任务→代码→TC→结果追踪、变更、验证、风险、回滚、人工决定 | 所有结论有证据，未验证项显式列出 |

## 追踪编号

- 需求或用户故事：`REQ-01`、`UC-01`。
- 验收标准：`AC-01`。
- 编码任务：`DEV-01`。
- 测试用例：`TC-01`。
- 审查问题：`REV-01`。
- 根因记录：`RCA-01`。

编号在同一任务内保持稳定。需求变更时更新受影响产物和 `00-run-plan.md` 的变更记录，不复用旧编号表达新语义。

## 测试用例独立性

验收、接口和 E2E 用例只依据需求计划、已确认 AC、接口契约和设计来源生成，不读取实现代码来决定期望结果。单元测试可以白盒读取实现。测试用例至少包含：类型、优先级、关联 AC、前置条件、测试数据、步骤、预期结果、自动化方式和证据要求。

自动化不可行时不得伪造结果。将用例标记为“未自动化”或“阻塞”，写明原因、人工验证步骤、风险和责任人。

## 测试执行证据

测试报告必须记录：

1. 基线、环境、工具版本和执行时间；
2. 实际命令及退出码；
3. 每条 TC 的通过、失败、阻塞或未执行状态；
4. 日志、截图、视频、覆盖率或机器报告的相对路径；
5. 失败分类、关联 RCA、修复版本和复测结果；
6. 汇总数量、未验证项和剩余风险。

证据保存到 `evidence/` 或项目既有测试报告目录，文档只引用相对路径。不得把密钥、客户数据或完整敏感响应写入证据。

同一命令在相关代码未变化时只记录一次通过证据。失败后先运行最小失败目标；定向通过后才扩大到受影响模块，最后才按风险执行环境验收。被数据库、账号、浏览器或外部密钥阻塞的 TC 直接记录为阻塞，不反复探测环境。

## 裁剪规则

- 新功能、跨模块变更、接口/数据/权限变更：全部产物必需。
- 普通缺陷修复：全部产物必需，需求计划可聚焦为现象、期望和回归 AC。
- 极小且无行为变化的修改：允许合并 `01`～`04` 到 `00-run-plan.md`，但必须保留对应章节、追踪编号和裁剪理由；测试与审查结果仍需落盘。
- 无测试框架或环境受阻不是省略依据，应输出用例和未执行结果，并记录阻塞证据。

使用 `assets/` 中的同名模板生成这些文件。
